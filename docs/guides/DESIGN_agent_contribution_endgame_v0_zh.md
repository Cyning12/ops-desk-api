## 1. 愿景与终局形态

**终局判断**：形似 Cursor / Claude Code 的 coding agent（编码智能体），神不似——差异化在**治理型骨架**：HITL（人在环审批）、租户隔离、台账审计是一等公民。终局更像「带治理闸的 Devin」：拿到 issue → 经 `_tech_graph`（技术图谱）分析生成方案 → 沙盒实际落地 → 给上游开源库提 PR（合并请求）。

**三步走战略**（维护者裁定 2026-10-09）：

```
第一步：先做 kimi-code 专用贡献 agent（问题域收敛 · 图谱专仓专建）
第二步：从专用版提取可复用 harness 框架（通用骨架与专用配置分层）
第三步：同步迁移落地到实际企业（ops-desk 本身就是企业载体 · tenant_id 已贯穿）
```

**专用/通用分层线**（做专用版第一天就要按两层写，否则提取等于重写）：

| 通用骨架（未来的 harness） | kimi-code 专用（示例/配置） |
|---|---|
| 事件溯源 run 循环（lg-rag multi + 事件表） | 该仓的 _tech_graph 实例 |
| capability gateway（能力网关）+ HITL + 委派令牌 | 该仓的读码/测试/构建 capability 注册 |
| 沙盒 runner 接口（worktree 工作树/容器/资源帽） | 该仓的测试命令、lint（静态检查）门槛 |
| PR 工作流（fork 派生/分支/合规检查） | DCO/CLA 规则、提交信息风格 |
| 方案生成 prompt 框架 | kimi-code 领域知识、目录约定 |

## 2. 阶段路线与时间预期

```
P0（已完成）：D 组写面零突破 + A/B 观测面（工具列表页 · 全量过程展示 · SSE 导出）
P1        ：issue → 图谱分析 → 方案文档（人审出口）          【1~2 周】
P2（分水岭）：方案 → 沙盒 worktree 落地 → 目标仓测试 → diff 提案（HITL 审批 diff）【2~4 周】
P3        ：diff → 自动 PR（合规面）→ 上游 review 评论回读再修  【+1~2 周】
```

**节奏口径**（2026-10-09 重估 · 取代早期「半年」口径）：以本项目实证节拍（chat-history-hitl-ux 全链 1 天：SPEC→审查→签闸→实现→PR→CLOSE）为基准，**P1+P2 全链 4~8 周到首个 PR 提交**；维护者确认闸延迟（长假）非常态后，预期可压向前段。**不可压缩项**：方案质量的迭代收敛（靠评测集跑分而非感觉）、上游 review 节奏（外部变量 · 里程碑钉「提交高质量 PR」而非「被合入」）。

**P2 设计纪律第一条**：目标仓测试必须绿才允许提 PR——这是治理体系相对野生编码机器人的立身之本。

## 3. 设计纪律

### 3.1 图谱与版本钉死（维护者令 2026-10-09 置顶）

- **图谱真址**：`/Users/cyning/Desktop/Projects/kimi-code-meta/docs`（`_tech_graph` 三层 l0/l1/l2/shared + tasks/standards · 与 ops-desk 同套方法论 · 预计 2026-10-10 完工）
- **每次 issue 任务前必须先检查目标仓库是否最新**（拉取/校验 HEAD）；不是最新则先同步
- **执行全程必须留下可钉死的仓库版本标识**：方案文档、沙盒落地、diff 提案、PR 描述，每一环都记录目标仓的 commit hash（或 tag）；任何结论可追溯回「基于哪个版本做的」
- **图谱保鲜**：图谱过期 = 错误方案。裁定项：重建节奏（每次分析前增量 vs 每日全量）+ **图谱构建 agent 化**（让 agent 读 diff 自更新图谱 · 最值得 dogfood「自家用自家产品」的一环）

### 3.2 安全与信任（P2 开工闸级）

- **沙盒安全模型写成设计纪律**：网络隔离（默认断网 · 依赖拉取走白名单）· 密钥隔离（沙盒内零 LLM 密钥、零 GitHub 写权限令牌）· 资源帽（CPU/内存/时长上限）· 文件系统隔离（只能动自己的 worktree）· **一键终止必须实现**（capability 清单已留 `requires_stop_support` 字段位）
- **供应链防线（维护者修正版）**：**kimi-code 仓不允许 agent 添加新依赖**（锁文件为准）；但**保留可人工打开的标记**（配置开关 · 默认关）——为后续通用化/其他仓做准备，通用版按仓策略配置
- **渐进放权（graduated autonomy）**：第一级「只出方案文档」→ 第二级「出 diff 人逐行审」→ 第三级「低风险类目（文档/测试补充）自动 PR，代码改动仍人审」。每级跑够成功率再升，直接缓解审批疲劳
- **失败的经济学**：单 issue 总重试上限 + 超限自动升级人工（挂 `budget.py` 预算模块）；不许 agent 无限自我拉扯

### 3.3 质量与评测（P1 就要建）

- **评测集先行**：10~20 个 kimi-code 真实 issue 建金标准评测集（含已被上游解决的标准答案）；方案质量靠跑分不靠感觉 · 复用仓内 langfuse 评测链路
- **运营看板（维护者特别强调 · ROI 汇报用）**：方案通过率 / 测试通过率 / PR 存活率 / 单 issue 成本 / 平均周期——复用 sli-four-metrics（四项服务指标）方法论 + token 成本台账（eval-token-cost-ledger 先例）；**单 issue 成本上限钉死，超了自动停**

### 3.4 合规与社区（P3 前置 · P2 中段查清）

- **上游 AI 政策**：查清 kimi-code 贡献指南与 AI 生成内容政策；PR 描述主动披露「AI 生成 + 人工审核背书」
- **许可证与身份**：AI 生成代码的许可归属 · DCO/CLA 签署主体 · **专用机器人账号提交**（明确 bot 标识 · 不用个人号）
- **社区礼仪限额**：每周 1~2 个高质量 PR 上限；P3 必做「review 评论 → 修改 → 再推」回环——上游维护者的耐心是最稀缺的外部资源

### 3.5 企业化前瞻（现在不写码 · 别埋雷）

- **数据边界**：专用版读公开仓可发外部大模型 API；企业版读私有代码须换私有部署模型/企业级端点。「读码 → 送模型」链路的**内容出口做成可配置面**，企业版切换零改造
- **多租户身份**：PR 机器人凭证、审批人、成本归集挂进 `tenant_id` 维度（事件/归属已贯穿 · 顺势延伸）

## 4. 架构决议摘要（2026-10-09 讨论沉淀）

| 议题 | 决议 |
|---|---|
| **MQ（消息队列）** | HITL 核心（状态机+恢复）**不需要 MQ**：PG 审批表 + 事件表共享真源已覆盖；MQ 企业价值仅在通知扇出与异构系统集成，以 **Outbox（发件箱）模式**可插拔引入（与状态机同事务写 outbox 表 · relay 搬运工出口可换 webhook/Kafka）· 不进架构中心 |
| **批准后自动继续** | **不需要 MQ**：两零件 = 触发器（进程内后台任务 / PG 轮询工人 / PG LISTEN-NOTIFY 推送三选一）+ 补偿扫描（启动时+定时扫「已批准未恢复」· 无状态恢复保证幂等）；多副本用数据库行锁认领防重。自动/手动做成**可配置**（全局默认 + 可按审批单选「立即执行/稍后手动」） |
| **无状态恢复纪律** | 任何时候不得引入「恢复依赖进程内存」的挂起态——一旦破坏，MQ/会话粘连全部被迫进场；当前 resume 从事件表重建是对的，SPEC 级锁死 |
| **Redis** | catalog 从来不是 Redis 设计（manifest 进程内注册表）；Redis 唯一留位 = 多副本熔断共享态（`circuit_storage.py` · 显式 degraded 降级设计 · 挂了不瘫痪）。**单机/2C4G/本机部署不需要 Redis** |
| **部署拓扑** | P1 零新增服务（PG + qdrant + api + web + 外部 LLM API）；P2 唯一新增 = **沙盒执行容器**（瞬态 `docker run --rm --cpus --memory` + worktree 卷 · 2C4G 上 api 进程内 asyncio worker 串行即可 · 不上独立服务不上 Redis 队列） |
| **能力形态** | tech_graph 读取 = 注册 capability（`side_effect: read` · local_fn 一期）；MCP（跨宿主直读）留二期，与 local_fn 共享同一 graph-query service 层不返工 |
