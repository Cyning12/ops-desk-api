### 0.1 CI 能力边界


| 能力项                        | 是否支持 | 说明                         |
| -------------------------- | ---- | -------------------------- |
| YAML → MD 编译               | 是    | 生成物与 YAML 源一致              |

**定稿表述**：

## 3. 低分项深挖（只分析 · 本文件不实施）

本节对应评分最低的两项：**协议落地度（★★★）**、**代码漂移控制（★★★）**。  
目标：厘清「低」的含义、可接受区间、以及若要抬分时的最小路径——**不**在本波改 YAML / CI / AGENTS。

### 3.1 协议落地度 ★★★



#### 问题本质

- **完备度高、落地度中**：规范已是目标态；业务图停在「主干 Happy Path + 基础顺序流」。
- 低分不表示协议失败，而表示 **定义面 ≫ 使用面**，评测按「已兑现能力」扣分是合理的。



#### 当前优先策略（为何合理）


| 观察                        | 解读                                                  |
| ------------------------- | --------------------------------------------------- |
| auth 边 14/14 有锚点          | 鉴权主链已可追溯，落地优先级高                                     |
| chat / sync / main 仍有无锚点边 | 结构边、跨图指针、示意边可能被有意省略                                 |
| 几乎无 `[err]` / 条件边         | 与「先保主干通畅」一致；异常路径多在 task `failure_paths` / 代码里，未升格进图 |




#### 抬分杠杆（按性价比）


| 优先级 | 动作                                                           | 预期收益             | 成本 / 风险      |
| --- | ------------------------------------------------------------ | ---------------- | ------------ |
| P0  | 补齐 **硬边** 缺失 anchors（尤其 `10_flow_chat` 无锚 8 条）               | 落地分↑；AI/人读图可跳转源码 | 低；需人工对行号     |
| P1  | 在 auth / chat 各选 **1～2 条** 真实 sad path 标 `[err]` 或 `::gates` | 证明协议非空转；不要求全量异常树 | 中；选错边会误导     |
| P2  | 对 LangGraph 条件分支用 `?>`（intent 路由等）                           | 与实现同构，利于 Agent   | 中；条件标签须与代码一致 |
| P3  | 全量异常 / 重试 / timeout 入图                                       | 评分观感满分           | 高；图噪声↑，维护税↑  |


**建议定调**：落地度目标保持 **「主干 + 关键 sad path 抽样」**，不要追求协议全字段刷满。★★★→★★★★ 通常只需 P0+P1；冲 ★★★★★ 性价比低。

#### 验收口径（若未来开 task）

- 硬边 anchors 覆盖率阈值（例如 G-L1 flow 图 ≥90%），由 task 写明；是否进 CI `--check` 另议。
- `[err]` / `::gates`：**抽样存在性**验收，非「每条调用必有 err 边」。

### 3.2 代码漂移控制 ★★★



#### 问题本质

- 漂移控制被拆成：**文档自洽（CI 已强）** vs **语义覆盖（机械弱）**。
- ★★★ 反映的是「意图有纪律、执行靠人/Agent 自觉」，不是「完全无控制」。
- `HG-GRAPH-MODULES` 只护 **模块边界表**，不护 **flow 漏画**——这是架构选择，不是实现遗漏 alone。



#### 控制面分层（现状）


| 层      | 机制                                    | 拦什么                        | 不拦什么                  |
| ------ | ------------------------------------- | -------------------------- | --------------------- |
| CI     | `tech-graph.yml` → `graph-compile.sh` | YAML/MD/JSON 不一致           | 漏画、错画、锚点过期            |
| 会话闸    | active task · GATE_VERIFY · HG-       | 无 task / 闸 pending 的 30 改码 | 有 task 且闸已签后的漏更新 flow |
| 纪律条文   | AGENTS「新增路由/表/事件须同步图谱」                | 无机械效果                      | —                     |
| Review | 推断关注，非成文 checklist                    | 取决于人                       | 无强制条目                 |




#### 抬分杠杆（按侵入性）


| 档       | 动作                                                            | 漂移控制分      | 说明                       |
| ------- | ------------------------------------------------------------- | ---------- | ------------------------ |
| A · 低侵入 | PR 模板勾选项：「涉及路由/表/事件？→ 已更新 `_tech_graph`」                      | ★★★ → ★★★☆ | 仍非强制机器；把推断写成文            |
| B · 中侵入 | task 字段 / wiki_delta 类：声明 `graph_paths_touched`；lint 缺字段 warn | ★★★☆～★★★★  | 与现有 harness task 习惯接近    |
| C · 高侵入 | 源码符号/路由装饰器 ↔ YAML anchors 比对（warn→error）                      | ★★★★～★★★★★ | 真正的 drift gate；误报与维护成本最高 |


**建议定调**：短期用 **A 或轻量 B** 抬「组织可观测性」；**C 单独立项**，勿与「补 `[err]`」绑同一 task。当前 ★★★ 对「小团队 + Agent 会话闸」是可接受稳态，除非漏画已造成多次线上/评审事故。

#### 验收口径（若未来开 task）

- A：模板存在且文案与 AGENTS 纪律对齐即可。
- B：缺字段可 warn；是否 `--strict` 进 CI 需维护者拍板。
- C：先 shadow/warn 一期，再谈 error；明确「只扫已登记 path glob / 已画 graph_id」。

## 4. 两项低分的关系

```text
协议落地度低  ≠  漂移控制弱的同一缺陷
     │                    │
     │                    └─ 「该画的没画 / 画了与代码脱节」无人/无机关
     └─ 「协议能力用薄」——图仍可能与代码一致，只是表达贫乏
```

- 只补 `[err]` **不**自动提高漂移控制（仍可不画新路由）。
- 只做 drift lint **不**自动提高协议落地（仍可全是 `->`）。
- 若只能开一个后续 task：先定痛点——**漏画事故多 → 偏漂移（A/B）**；**Agent 读图经常猜错分支/鉴权 → 偏落地（P0/P1）**。
